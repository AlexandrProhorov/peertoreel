# ADR-0003: Drizzle ORM and drizzle-kit migrations

- **Дата:** 2026-11-02
- **Статус:** accepted

## Контекст

M0 начался с `pg.Pool` и собственного SQL migration runner. Это было полезно для обучения,
но дальше появляются бизнес-таблицы, связи, транзакции и типизированные запросы. Поддерживать
свой migration runner и вручную описывать типы строк — лишняя работа.

Рассматривались:

- raw `pg` — слишком много ручного маппинга;
- Kysely — хороший typed query builder, но нужен отдельный слой описания схемы;
- Prisma — скрывает SQL и навязывает свой workflow;
- TypeORM — много декораторов и неявного поведения;
- Drizzle — схема в TS, типы из схемы, SQL-прозрачность, стандартные миграции.

## Решение

Используем **Drizzle ORM + drizzle-kit**.

- `apps/api/src/db/schema.ts` — единственный источник описания таблиц.
- `DatabaseService` создаёт `pg.Pool` и `drizzle(pool, { schema })`.
- Репозитории получают `DatabaseService.db`.
- Миграции генерируются `drizzle-kit generate` в `apps/api/drizzle/` и коммитятся.
- Применение — `drizzle-kit migrate`.
- `drizzle-kit push` запрещён для production; допустим только для локальных экспериментов.
- Старый `src/db/migrate.ts` и `migrations/0001_init.sql` удалены.
- Старая таблица `schema_migrations` удалена custom-миграцией; историю ведёт Drizzle.

## Последствия

- Схема и типы живут в одном месте.
- Сгенерированный SQL нужно читать перед коммитом.
- Применённые миграции нельзя редактировать.
- Для локальной БД, созданной старым runner'ом, первая миграция сделана идемпотентной
  (`CREATE TABLE IF NOT EXISTS`), чтобы не удалять volume.
- Drizzle не отменяет знание SQL: сложные запросы и транзакции всё равно пишем явно.
